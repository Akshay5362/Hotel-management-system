## 1. Executive Summary

- **Progress Across Optimization Phases:**
  - **Pre-Optimization Baseline:** ~33K reads/day (~1.4K–2.5K reads/hour) with frequent quota exhaustion warnings.
  - **Phase 1 (Room Status):** Optimized `/api/status` with 30s TTL, single-flight coalescing, and mutation invalidation.
  - **Phase 2 (Guest Requests):** Optimized `/api/admin/guest-requests` with 15s TTL, targeted index-free queries, and single-flight coalescing.
  - **Phase 3A (Guest Directory):** Optimized `/api/admin/guests` with 15s TTL, in-memory filtering/search/KPI stats, and mutation invalidation.
  - **Current Run Rate:** ~1.4K reads/hour ($\approx 33,600 \text{ reads/day}$), representing **67.2% of the daily 50K free quota** (16.4K reads daily headroom).
- **Core Findings of this Audit:**
  1. **Primary Steady-State Read Generator (~1,440 reads/hr / 100% of steady-state):**
     - Background room status polling (`GET /api/status`) from `App.jsx` (20s interval) and `ReceptionPortal.jsx` (30s interval). With 30s TTL, this triggers ~120 cold fetches/hour $\times$ ~12–24 document reads $\approx \mathbf{1,440 \text{ reads/hour}}$.
  2. **High-Risk Latent Read Amplification Vector (Up to ~13,800 reads/hr during guest sessions):**
     - `GET /api/guest/bill` in `GuestDashboard.jsx` is polled every **30 seconds** (`setInterval`) while a guest is logged in.
     - `AuditHistoryCutoverService.getGuestBill` performs full scans on `getAllGuestsFirestore()` (~62 reads) + `getAllBookingsFirestore({ limit: 50 })` (~50 reads) + `ledger_items` (~3 reads) = **115+ document reads per request**.
     - A single active guest session generates $\mathbf{13,800 \text{ reads/hour}}$ if left open.
  3. **Explanation of Observed Writes (~923/hr) and Deletes (~167/hr):**
     - These metrics were **100% generated by test suite executions** run over the last hour (`testComprehensiveRoomShiftBillingAndAdjustments.mjs`, `testRoomShiftBillingAndCheckoutEnforcement.mjs`, `testCheckInGenderAndPincode.mjs`, etc.) which create temporary isolated fixtures and delete them in cleanup hooks.
     - In steady-state operational use without test runs, HPMS produces **<20–50 writes/hour** and **0 routine deletes**.

## 7. Folio / Master Bill Audit

- **Reception / Staff Master Bill (`/api/rooms/:id/master-bill`):**
  - Uses targeted indexed lookups: `rooms.doc(id)` (1 read), `bookings.doc(id)` (1 read), `guests.doc(id)` (1 read), `ledger_items.where('booking_id')` (~3 reads), `payments.where('booking_id')` (~2 reads).

- **Guest Portal Live Folio (`/api/guest/bill`):**
  - **Flawed implementation in `AuditHistoryCutoverService.getGuestBill`:**
    - Scans all guests to find `user_id == resolvedUserId` (62 reads) instead of `guests.where('user_uid', '==', ...)` or direct doc lookup.
    - Scans 50 bookings to find `guest_id == id` (50 reads) instead of `bookings.where('guest_id', '==', id)`.
    - Total: **115+ reads per request**, multiplied by **30-second polling**.

## 13. Top 5 Remaining Read Amplification Sources

1. **Room Status Polling Interval vs. TTL Alignment (`/api/status`):**
   - Generating ~28,800 reads/day. Polling every 20s while TTL is 30s causes cache expiration every other poll.
2. **`GET /api/guest/bill` Uncached Full Scans (`AuditHistoryCutoverService.getGuestBill`):**
   - Generates 115 reads per request on 30s polling when a guest is logged in. Potential to consume 13.8K reads/hr per guest session.

   - Performs `getAllBookingsFirestore(100)` + `getAllPaymentsFirestore(100)` (~125 reads).

   - Scans entire payments, bookings, and rooms collections (~149 reads/cold report).
5. **ID Document Verification Scans (`GuestAdminService.getGuestDocuments`):**

## 15. Recommended Optimization Priority (For Future Review)

1. **Priority 1 (Phase 3B — Highest Impact): Fix `AuditHistoryCutoverService.getGuestBill` & `getGuestHistory`:**
   - Replace full scans of `guests` (62 reads) and `bookings` (50 reads) with direct `where` queries or doc ID lookups:
     - `guests.doc(guestId)` (1 read)
     - `bookings.where('guest_id', '==', guestDocId)` (1–3 reads)
     - `ledger_items.where('booking_id', '==', bkgDocId)` (1–3 reads)
   - **Expected Read Reduction:** Reduces single guest bill request from **115 reads $\rightarrow$ 3–5 reads (96% reduction)**. Eliminates the 13.8K reads/hr latent risk.
2. **Priority 2 (Phase 3C): Reports & Analytics Date-Bounded Queries:**
   - In `FirestoreReportsService`, query `payments` and `bookings` with Firestore date bounds (`where('business_date', '>=', startDate)`) instead of reading entire collections.
   - **Expected Read Reduction:** 50–70% reduction on cold report generation.
3. **Priority 3: Room Status Polling Interval Realignment:**
   - Align frontend polling in `App.jsx` from 20s to **30s** to match the 30s backend cache TTL.
   - **Expected Read Reduction:** Reduces baseline status reads from ~1,440 reads/hr $\rightarrow$ **~720 reads/hr (50% reduction)**.

## 16. Risks of Proposed Future Optimizations

- **`getGuestBill` Query Refactoring:** Must ensure that legacy guests with format `guest_<phone>` vs integer IDs match reliably without falling back to collection scans.
- **Reports Date Range Queries:** Composite index requirements in Firestore when mixing `where` and `orderBy` on date fields. Must use memory sorting if indexes are avoided.
- **Polling Interval Realignment:** Increasing polling interval from 20s to 30s could add a slight 10s visual delay for room status updates if websockets are disconnected.
